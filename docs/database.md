# Database Design

PostgreSQL, managed via Prisma (`prisma/schema.prisma`). This document
explains the entity relationships and design decisions; the schema file
itself is the authoritative source.

## Entity-relationship overview

```
User (dashboard operators — not linked to Vehicle/Accident directly)

Vehicle ──1───N── SensorReading
   │                    │
   │                    │ N
   1                    │
   │                    1
   N                    │
Accident ──1───N── AccidentSensorSnapshot
   │  │
   │  └──N───1── PoliceStation  (nullable FK: nearestPoliceStationId)
   │  └──N───1── Hospital        (nullable FK: nearestHospitalId)
   │
   1
   N
Notification ──N───1── PoliceStation (nullable)
              ──N───1── Hospital       (nullable)
```

## Entities

### User
Dashboard/operator accounts (login credentials). Not linked to vehicles —
this is an operations console, not a customer-facing app, so any operator
can view any vehicle/accident.

### Vehicle
Registration and owner metadata, plus an optional `deviceId` — the field a
real ESP32 would identify itself with (a future hardening step, described in
`hardware-integration.md`, would match incoming sensor data against this).

### SensorReading
Every raw telemetry reading, whether from the simulator or real hardware
(`source` enum distinguishes them). This table is the permanent, complete
record — nothing is ever deleted from it, even readings that don't trigger
an accident. It backs the "recent sensor readings" view on the vehicle
details page.

### Accident
The core record. Stores the full snapshot needed for the accident details
page in denormalized form (`speedBeforeImpact`, `impactSpeed`,
`speedAfterImpact`, peak acceleration/gyro on all 3 axes, `severity`,
`confidenceScore`) rather than requiring the frontend to recompute anything
from raw sensor rows — this keeps the accident details page a single API
call.

### AccidentSensorSnapshot
A join table linking an `Accident` to the specific `SensorReading` rows that
made up its before/impact/after timeline (`relativePosition`: `BEFORE` |
`IMPACT` | `AFTER`, plus `offsetMs` for exact chronological placement). This
is what powers the sensor timeline chart on the accident details page,
without duplicating sensor data into the `Accident` row itself.

### PoliceStation / Hospital
Separate tables (not a single polymorphic "Agency" table) because their
attributes are identical today but are likely to diverge in a real system
(e.g. hospitals might later need a `bedCapacity` or `traumaCenter` field) —
keeping them separate avoids a premature abstraction.

### Notification
One row per (accident, recipient type) pair — so a single accident always
produces exactly two rows (POLICE and HOSPITAL), each independently
trackable through `PENDING → SENT/FAILED → ACKNOWLEDGED`.

## Why these indexes

| Index | Reason |
|---|---|
| `SensorReading.vehicleId`, `[vehicleId, timestamp]` | Every buffer/history lookup filters by vehicle and orders by time |
| `Accident.vehicleId` | Vehicle details page's accident history |
| `Accident.occurredAt` | Dashboard "accidents today" and trend queries |
| `Accident.severity`, `Accident.status` | Accidents page filters |
| `Accident.[latitude, longitude]` | Supports future geo-range queries |
| `PoliceStation.[latitude, longitude]`, `Hospital.[latitude, longitude]` | Supports future geo-range queries (current mock lookup does an in-memory Haversine scan since station/hospital tables are small — the index still helps as this table grows) |
| `Notification.accidentId`, `.status`, `.recipientType` | Dashboard pending-notification counts, accident details page |

## Why Prisma over raw SQL / a lighter ORM

Prisma was chosen specifically because its generated client gives compile-
time-checked query shapes and its `schema.prisma` file doubles as
human-readable documentation of the entire data model — valuable both for
development speed and for viva presentation, where the schema file itself
can be shown on screen as the "database design" artifact.

## Migrations

Migrations live in `prisma/migrations/` (auto-generated by
`npx prisma migrate dev`, not hand-written). `prisma/seed.js` populates
demo data — vehicles, police stations, hospitals, sample sensor readings, and
one historical sample accident — for a working dashboard on first run.
